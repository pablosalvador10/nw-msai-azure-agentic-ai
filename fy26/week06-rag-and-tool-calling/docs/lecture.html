1. Why models need sources and tools

A model has three blind spots that no prompt can fix.

Blind spotExample at Lakeshore RideFix
Private knowledge. It never read your documents."What is the lost e-bike fee?"Retrieval (RAG)
Freshness. Its knowledge stops at a training cutoff."Did the student plan change this month?"Retrieval over current documents
Computation and live state. It predicts text; it does not calculate or observe."What does a 50-minute ride cost?" "Are there e-bikes at LS-08 now?"Tools: your code

Without the handbook

Asked for the lost e-bike fee, one run answered "I don't have enough information to know Lakeshore Ride's specific policy…", then general guesses.

2. Embeddings and similarity

An embedding model maps text to a vector so that texts with similar meaning point in similar directions, even with no words in common. text-embedding-3-small returns 1,536 numbers per text.

cos(a, b) = (a · b) / (‖a‖ ‖b‖)

Cosine is 1 for the same direction and near 0 for unrelated texts. These embeddings are normalized to length 1, so cosine equals the plain dot product, which is why vector indexes can compare millions of vectors quickly.

Compared with "fee for a lost e-bike"Cosine
"what you pay if an electric bike goes missing"0.801
"station opening hours"0.183
Lab Part 2, one run. The first pair shares almost no words and still scores high.
  • Similarity is a ranking signal, not a probability. Scores for relevant and irrelevant passages are often close (0.62 versus 0.48). Compare scores with each other; do not hard-code "relevant above 0.7".
  • Embed queries and documents with the same model. Vectors from different models live in different spaces.
  • Dimensions are a cost knob. The dimensions parameter shortens vectors with little quality loss: less storage, faster search.
  • Embeddings miss exact tokens. Station ids (LS-08), fee names and product codes are often better matched by keywords. Section 5 combines both.
  • Re-embed when you change models. An index is tied to the model that built it.

app/rag.py embeds every handbook section once at startup and ranks sections by cosine for each question. Offline mode replaces the model with a hashed bag-of-words vector, so tests run without Azure.

4. Chunking

A chunk is the unit you embed, retrieve and cite. Its size is a trade-off.

Chunks that are…RetrievalGenerationCitations
Too largeThe vector averages many topics; matches get vagueLots of irrelevant text in the contextCoarse: "somewhere on this page"
Too smallPrecise matchesMissing the sentence that gives the answer its meaningPrecise, but context is lost
StrategyIdeaWhen
Fixed size with overlapEvery n tokens, overlapping by mUnstructured text, baselines
Structure-awareSplit on headings, paragraphs, table rowsDocuments with structure: our handbook, one chunk per ## section
SemanticSplit where the topic shifts, measured by embedding distanceLong prose without structure
Parent-child ("small to big")Retrieve small chunks, send their larger parent sectionPrecise matching and full context

Always attach metadata: document id, title, section, date, and access-control information. Metadata powers citations, filters ("only the student plan pages") and permission trimming.

5. Retrieval: vector, keyword, hybrid, reranking

MethodMatchesStrengthWeakness
Keyword (BM25)Shared terms, weighted by rarityExact ids, names, codes, numbersSynonyms and paraphrases
VectorMeaningParaphrases, other languagesExact tokens, negation, rare ids
HybridBoth, fusedThe best of both; the default in productionTwo indexes to maintain
+ Semantic rerankerA cross-encoder rereads query and passage togetherMuch better ordering of the top resultsExtra latency per query

Fusing rankings, and reranking

Hybrid search runs both searches and merges the two ranked lists with Reciprocal Rank Fusion. A document's score is the sum, over the lists it appears in, of:

RRF(d) = Σr ∈ rankings 1 / (k + rankr(d)),   k usually 60

RRF needs no score calibration (BM25 and cosine scores are on different scales), which is why Azure AI Search uses it. A bi-encoder (the embedding model) encodes query and passage separately; a cross-encoder reads them together and judges relevance much better, but is too slow for the whole index. So retrieve broadly (say 50 candidates) and rerank narrowly.

Approximate nearest neighbor

At scale you cannot compare a query with every vector. Indexes such as HNSW find near-best matches in logarithmic time, trading a little recall for a lot of speed. Exhaustive search is still right for small collections like ours.

How many passages?

More raise recall and lower precision. Models attend best to the beginning and end of long inputs, the "lost in the middle" effect: put the best passages first and keep k small.

6. Generation: grounding, citations, abstention

The generation step turns passages into an answer you can trust. Three properties define "trust".

Grounded

Every claim is supported by a passage. Instructions say "answer only from the passages"; passages carry ids.

Cited

The answer says which passages support it: structured output with a citations list, validated against known documents.

Abstains

It says "I don't know" when the sources are silent: an abstained flag with a precise rule for when to set it.

Passages go in input, not in instructions. Retrieved text is data. If a document says "ignore your rules", it must be read, not obeyed. That is indirect prompt injection, Week 10's main topic.

Abstention is a product decision. A false "I don't know" annoys a rider; a confident wrong answer about a fee costs money and trust. The harness checks both directions (w06.ask.abstain).

Instead of one query, a model plans the retrieval, runs sub-queries in parallel against one or more sources, reranks and merges. In Foundry IQ you set a retrieval reasoning effort (minimal, low or medium) to trade latency for thoroughness.

Permissions are the hard part. Two employees asking the same question must get different answers if they can read different documents. Foundry IQ synchronizes access control lists and runs queries under the caller's Entra identity, so the agent retrieves only what the user could open. Building that yourself is a project; buying it is usually right.

9. Tool calling: the protocol

RAG gives the model text. Tools give it your code. The model never runs anything; it asks, and your code decides.

Where RAG stops: arithmetic

"I'm a member. What does a 50-minute classic ride cost?" The rules are in the handbook (45 minutes included, then $0.15 a minute), so the answer is $0.75, but the model must do arithmetic, and "sometimes right" is not good enough for a bill.

Where RAG stops: live state

"How many e-bikes are at LS-08 right now?" Live availability is in no document. One run with RAG alone answered "I don't know": honest, and useless.

PieceWhat it is
Tool definition{"type": "function", "name", "description", "parameters": <JSON Schema>, "strict": true}, sent with the request
function_call itemThe model's request: tool name, arguments as a JSON string, and a call_id
function_call_output itemYour result, sent back with the same call_id
The loopRepeat until a response contains no function_call items; that response is the final answer

The loop, by hand

def ask_with_tools(question: str) -> str:
    response = client.responses.create(
        model=MODEL, instructions=TOOL_INSTRUCTIONS,
        input=question, tools=TOOLS)
    while True:
        calls = [i for i in response.output if i.type == "function_call"]
        if not calls:
            return response.output_text   # no more requests: final answer
        results = []
        for call in calls:
            arguments = json.loads(call.arguments)
            result = FUNCTIONS[call.name](**arguments)
            results.append({"type": "function_call_output",
                            "call_id": call.call_id,
                            "output": json.dumps(result)})
        response = client.responses.create(
            model=MODEL, instructions=TOOL_INSTRUCTIONS,
            previous_response_id=response.id,
            input=results, tools=TOOLS)
OptionUse
tool_choiceauto (default), required, none, or one named function: force a lookup, or forbid tools for a turn
parallel_tool_callsSeveral independent calls at once: fare and station
strictArguments always match the schema: every property required, additionalProperties: false

Guard the loop. A maximum number of iterations and tool calls, a time budget, and errors returned to the model as data ("unknown station LS-99"), not raised. Without limits, one confused model can call tools until your quota is gone.

Business logic stays in code. The fare rules live in app/domain.py as deterministic Python. The model chooses which tool and which arguments; it never computes a price. Let the model do language and judgment; let code do arithmetic, state and anything with money.

10. Designing tools a model uses well

The model knows your tool only through its name, description and schema. Those are a prompt, and they deserve the same care.

PrincipleWeakStrong
Names say what it doeslookup, helper2quote_fare, get_station
Descriptions say when to use it"Gets fares.""Exact ride fee in US dollars for one ride. Always use this instead of computing prices."
Constrain argumentsplan: stringplan: "single" | "day_pass" | "member" | "student"
Describe every argumentminutesminutes: Ride length in whole minutes.
Return what the model needs, no moreThe whole station databaseOne station's bikes, e-bikes and docks
Errors are dataraise KeyError{"error": "Unknown station LS-99. Ids look like LS-07."}
Separate read from writeOne manage_account toolget_balance (safe) and issue_credit (side effect)
Few, distinct toolsTwenty overlapping toolsA handful, each with a clear boundary

Side effects need extra care

A tool that moves money or opens tickets (Week 7) should be idempotent where possible, validated in code (amount caps, rider exists), recorded, and, for high-impact actions, approved by a person: approval_mode="always_require".

Token budget

Every tool definition is sent on every call. Fifty tools can cost thousands of input tokens per request and degrade tool choice. Keep tool sets small per agent, or use tool search (Foundry toolboxes).

11. Tools across the stack

Know who executes the tool: that decides where your code, secrets and logs are.

KindExampleWho executesWhere it is defined
Function tool (client-side)quote_fare, get_stationYour processYour code; the schema is sent with each request
Hosted tool (platform-side)Code interpreter, file search, web search, Azure AI Search, image generationFoundry, in its sandboxAgent definition or request
Remote tool over a protocolMCP servers, OpenAPI endpoints, A2A agentsAnother serviceA connection or a toolbox

Hosted tools save you code but move execution out of your process: check data residency, cost per call and what is logged. Remote tools over MCP are Week 8's topic, when your own service becomes a tool server for other agents.

12. Agentic RAG: retrieval as a tool

The starting /v1/ask retrieves once, always, then generates. The improved version gives the model search_handbook as a tool. The difference is who decides.

Retrieve-then-generateRetrieval as a tool (agentic)
SearchesExactly one, with the raw questionZero, one or several, with queries the model writes
Multi-part questionsOne query for two topics: weakOne search per topic
Questions that need codeGuessesCalls quote_fare or get_station
Latency and costPredictable: one model callVariable: one model call per loop iteration
Failure modeBad retrieval, confident answerOver-searching, or not searching when it should

Agent Framework supports both styles: retrieval as a tool the model calls when it chooses, or as a context provider that injects passages before every run. Use a context provider when every question needs the knowledge; use a tool when the model must decide.

13. One agent with Microsoft Agent Framework

Writing the loop once teaches you how it works. Writing it in every service is how bugs happen. Microsoft Agent Framework is Microsoft's open-source SDK for agents and multi-agent workflows in Python, .NET and Go, the successor to Semantic Kernel and AutoGen. This week uses its single-agent half; Week 7 uses workflows.

from agent_framework import Agent, tool
from pydantic import Field

    minutes: Annotated[int, Field(description="Ride length in whole minutes.")],
    ebike: Annotated[bool, Field(description="True for an e-bike.")] = False,
) -> str:
    """Exact ride fee in US dollars for one ride. Always use this instead of computing prices."""
    ...


agent = Agent(
    client=state.models.agent_client(),  # FoundryChatClient: project endpoint + Entra ID
    name="lakeshore-ask",
    instructions=INSTRUCTIONS,
    tools=[search_handbook, quote_fare, get_station],
)
result = await agent.run(question, options={"response_format": AskAnswer})
answer: AskAnswer = result.value  # typed, validated structured output

The framework also speaks to Foundry's platform tools: FoundryChatClient has helpers that return hosted tool configurations (code interpreter, file search, web search, Azure AI Search, MCP) that you pass in tools=[...] next to your Python functions.

Report from execution, not from prose. app/tools.py defines the tools with @tool. Each records its call inside recording(state), so the API reports tool_calls (Week 6) and actions (Week 7) from what actually ran, not from what the model claims it did.

14. Summary

  1. Models lack private knowledge, freshness and computation.RAG fixes the first two; tools fix the third.
  2. RAG is chunk, embed, retrieve, generate.Find the failing stage before you change anything.
  3. Production retrieval is hybrid(keyword plus vector, fused with RRF) with a reranker.
  4. Trustworthy answers are grounded, cited, and abstain when the sources are silent.Retrieved text is data, never instructions.
  5. Evaluate retrieval and generation separately.
  6. On Azure:AI Search when you want control, Foundry IQ for permission-aware agentic retrieval over enterprise sources, the file search tool for quick document Q&A.
  7. Tool calling is a loop of function_call and function_call_output items.The model asks, your code acts. Guard the loop with limits.
  8. Tool design is prompt design:names, "when to use" descriptions, constrained arguments, errors as data, read separate from write.
  9. Agent Framework runs the loop, builds schemas, enforces limits and traces everything.You still own the tools and the instructions.

Typical misses, in order of impact

Tools not called

The instructions do not say when to use each tool. Be explicit: "Never compute prices yourself; call quote_fare."

Too many citations

The model cites everything it read. Ask it to cite only passages it used, at most three.

Abstains at the wrong time

Define it precisely: "only when no tool result or passage answers the question".

First goal: w06.ask.tools above zero. Then tune instructions. Keep the guardrail check and the offline branch at the top of ask(): the offline tests rely on them. The proof in reports/ shows the exact answer for every miss.

Words used here

Embedding
A vector that represents the meaning of a text; similar meanings point in similar directions.
Cosine similarity
The cosine of the angle between two vectors; a ranking signal, not a probability.
Chunk
The unit you embed, retrieve and cite.
BM25
The standard keyword ranking function: shared terms weighted by rarity.
Hybrid search
Keyword and vector search run together and fused, usually with RRF.
Reranker
A cross-encoder that rereads query and passage together to reorder the top results.
Grounded
Every claim in the answer is supported by a retrieved passage.
Abstention
Answering "I don't know" when the sources are silent.
Function call
A model's request to run a tool, with a name, JSON arguments and a call_id.
Agentic retrieval
A model plans sub-queries, runs them in parallel, reranks and merges the results.
