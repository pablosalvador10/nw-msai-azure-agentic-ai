Choosing the approach

Three ways to put knowledge into an answer. Know when each is right

Long context

Put all documents in the instructions.

Good for small, stable corpora and prototypes; pairs with prompt caching.
Bad for large or growing corpora: cost and latency grow with every token, and quality drops.

RAG ours

Retrieve only the relevant passages for each question.

Good for large, changing, permissioned knowledge; answers that cite sources.
Bad for questions that need the whole corpus at once.

Fine-tuning

Train the model on examples.

Good for style, format, narrow tasks, smaller models.
Bad for facts that change or must be cited. It teaches behavior, not a database.

Our handbook is ten pages and would fit in the prompt: Week 5 did exactly that to show caching. We use RAG because the technique scales, and because citations need passages.

It is not lying

It has never seen the handbook. The fix is not a bigger model: it is putting the right passage in front of the model at question time.

Embeddings

Embeddings place texts with similar meaning close together, even with no shared words

Cosine similarity

cos(a, b) = a · b / (|a| |b|)

1 means the same direction; near 0 means unrelated. text-embedding-3-small returns 1,536 numbers, normalized to length 1, so cosine equals the plain dot product. Vector indexes rely on that.

Lab Part 2 · compared with "fee for a lost e-bike"Cosine
"what you pay if an electric bike goes missing"0.801
"station opening hours"0.183
  • A ranking signal, not a probability. Compare scores with each other; never hard-code "relevant above 0.7".
  • Same model for queries and documents. Vectors from different models live in different spaces.
  • Dimensions are a cost knob. The dimensions parameter shortens vectors with little quality loss.
  • Embeddings miss exact tokens: LS-08, fee names, codes. Keywords catch them.

Chunking

A chunk is the unit you embed, retrieve and cite. Its size is a trade-off

Chunks that areRetrievalGenerationCitations
Too largeVague matchesIrrelevant text in context"Somewhere on this page"
Too smallPrecise matchesThe sentence that gives meaning is missingPrecise, context lost

Always attach metadata: document id, title, section, date, access. It powers citations, filters and permission trimming.

StrategyIdea
Fixed size with overlapEvery n tokens, overlapping by m. A baseline
Structure-aware oursSplit on headings: one chunk per ## section of the handbook
SemanticSplit where the topic shifts, by embedding distance
Parent-childRetrieve small chunks, send their larger parent section

Retrieval

Production retrieval is hybrid: keywords plus vectors, then a reranker

MethodStrengthWeakness
Keyword (BM25)Exact ids, names, codes, numbersSynonyms, paraphrases
VectorMeaning, paraphrases, other languagesExact tokens, negation, rare ids
HybridBoth, fused: the production defaultTwo indexes to maintain
+ RerankerA cross-encoder rereads query and passage togetherExtra latency per query

Fusing two rankings

RRF(d) = Σ 1 / (k + rankr(d)), k ≈ 60

Reciprocal Rank Fusion needs no score calibration: BM25 and cosine live on different scales.

Keep k small, best first

Models attend best to the start and end of long inputs: lost in the middle.

Abstention is a product decision

A false "I don't know" annoys a rider; a confident wrong fee costs money and trust. The harness checks both directions.

Lab Part 3

Where RAG stops: arithmetic and live data need code, not text

"I'm a member. What does a 50-minute classic ride cost?"

The rules are in the handbook: 45 minutes included, then $0.15 a minute. The answer is $0.75. The model must do arithmetic, and models are unreliable calculators. "Sometimes right" is not good enough for a bill.

"How many e-bikes are at LS-08 right now?"

Live availability is in no document. No amount of retrieval can find it. One run with RAG alone answered "I don't know", which is honest and useless.

The business already has this code: app/domain.py computes fares exactly and reads station data. The model needs a way to call it.

The protocol

The model never runs your code. It asks, and your code decides

Repeat steps 2 to 5 until a response has no function_call items. That response is the final answer. That exchange is the loop.

Lab Part 4

The loop by hand: twenty lines you will never need to write again

def ask_with_tools(question: str) -> str:
    response = client.responses.create(
        model=MODEL, instructions=TOOL_INSTRUCTIONS,
        input=question, tools=TOOLS)
    while True:
        calls = [i for i in response.output if i.type == "function_call"]
        if not calls:
            return response.output_text   # no more requests: final answer
        results = []
        for call in calls:
            arguments = json.loads(call.arguments)
            result = FUNCTIONS[call.name](**arguments)
            results.append({"type": "function_call_output",
                            "call_id": call.call_id,
                            "output": json.dumps(result)})
        response = client.responses.create(
            model=MODEL, instructions=TOOL_INSTRUCTIONS,
            previous_response_id=response.id,
            input=results, tools=TOOLS)
OptionUse
tool_choiceauto, required, none, or one named function
parallel_tool_callsSeveral independent calls at once: fare and station
strict: trueArguments always match the schema, so **arguments never crashes

Guard the loop. A maximum number of iterations and tool calls, a time budget, and errors returned to the model as data, not raised. Otherwise one confused model spends your quota.

The most important design rule

Let the model do language and judgment. Let code do arithmetic, state and money

Model chooseswhich tool, which arguments, how to phrase the answer
→
Code decidesquote_fare, get_station: deterministic Python in app/domain.py
→
Code recordsevery call inside recording(state), so the API reports what actually ran

Report from execution, not from prose

Your tool_calls (Week 6) and actions (Week 7) come from the record of what ran, never from what the model says it did.

Side effects need more care

A tool that moves money should be validated in code, recorded, idempotent where possible, and approved by a person when the stakes are high. Week 7 shows how.

Part 3 · Lab Parts 5-6

The same, with Microsoft Agent Framework

Writing the loop once is how you understand it. Writing it in every service is how bugs happen.

Agentic RAG

Retrieve once and always, or let the model decide when to search

Retrieve-then-generate starting codeRetrieval as a tool your job
SearchesExactly one, with the raw questionZero, one or several, with queries the model writes
Multi-part questionsOne query for two topics: weakOne search per topic
Questions that need codeGuessesCalls quote_fare or get_station
Latency and costPredictable: one model callVariable: one model call per loop iteration
Fails byBad retrieval, confident answerOver-searching, or not searching when it should

Agent Framework supports both: retrieval as a tool the model calls when it chooses, or as a context provider that injects passages before every run.

Measure, then fix

Typical misses, in order of impact

Tools not called

The instructions do not say when to use each tool. Be explicit: "Never compute prices yourself; call quote_fare."

A rule and a number

"What credit do I get?" needs the rule from the handbook and the amount from quote_fare. Say so, with one worked example.

A price without its page

When a policy shapes a price (the fare cap), search the handbook too and cite that page.

Too many citations

The model cites everything it read. Ask it to cite only passages it used, at most three.

Abstains at the wrong time

"Only when no tool result or passage answers." Silence is not an answer: never infer a "no".

100 is reachable. Start with w06.ask.tools above zero, deploy once you beat the baseline, then fix one cause at a time. The proof in reports/ shows the exact answer for every miss.

Summary

What to remember

  • Models lack private knowledge, freshness and computation. RAG fixes the first two; tools fix the third.
  • RAG is chunk, embed, retrieve, generate. Find the failing stage first.
  • Production retrieval is hybrid, with a reranker.
  • Trustworthy answers are grounded, cited, and abstain. Retrieved text is data, never instructions.
  • Tool calling is a loop of function_call and function_call_output. The model asks; your code acts. Guard the loop.
  • Tool design is prompt design: names, "when to use", constrained arguments, errors as data.
  • Money, state and arithmetic live in code. Report what ran, not what the model says.
  • A framework saves you from rewriting the loop, not from understanding it.
