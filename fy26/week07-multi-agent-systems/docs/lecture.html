Multi-Agent SystemsWhen to split one agent into a team, how to orchestrate it, how to keep a person in the loop, and how to prove the split paid off.

Your service can answer questions. Now it must resolve cases: decide what a rider is owed, issue credit, open maintenance tickets, and reply. One agent with every tool and a two-page prompt works until it does not: it mixes up responsibilities, calls tools it should not, and becomes impossible to debug. Splitting the work among specialists, each with its own instructions and only the tools it needs, gives clearer behavior, parallel work and least privilege. It also costs more calls, more latency and more ways to fail. This lecture is a deep tour of Microsoft Agent Framework through that trade-off.

1. Agents, workflows, multi-agent systems: when to split

Three designs, in increasing order of autonomy and cost.

DesignWho decides the next stepStrengthWeakness
Single agent with toolsThe model, in one loopSimple; one context; cheapestOne long prompt; every tool always available; hard to debug as it grows
WorkflowYour code: a fixed graph of steps, some of them agentsPredictable, testable, auditableRigid: only handles the paths you drew
Multi-agent systemAgents decide together: handoffs, a manager, a group chatFlexible on open-ended tasksMore calls, more latency, more ways to fail

Agent Framework's own rule: if you can write a function to handle the task, do that instead of using an AI agent. Use a workflow when the process has well-defined steps; use an agent when the task is open-ended.

A shared vocabulary of patterns

Pattern names from Building effective agents (Anthropic).
PatternShapeAgent Framework construct
Prompt chainingStep A's output is step B's inputSequentialBuilder, or edges in WorkflowBuilder
RoutingClassify, then send to one specialistTriage agent with structured output, switch-case edges
ParallelizationIndependent subtasks at once, then mergeConcurrentBuilder, fan-out and fan-in edges
Orchestrator-workersA manager plans and delegates dynamicallyMagenticBuilder, or agents as tools
Evaluator-optimizerOne agent drafts, another critiques, repeatA loop edge, or GroupChatBuilder with two participants

Reasons to split, and the bill

  1. Instructions conflict."Be concise for riders" and "explain every policy clause" belong to different roles.
  2. Least privilege.Only one role should be able to move money.
  3. Parallelism.Independent lookups can run at the same time.
  4. Context hygiene.A specialist sees only what it needs.
  5. Separate evaluation.Measure and improve each role on its own.
≈ 15×the tokens of a chat, for Anthropic's multi-agent research system
86%three agents, each right 95% of the time, failing independently: 0.95³ (arithmetic)

Every split adds calls, latency and a new boundary where one agent knew something the next did not. Anthropic wins on broad research with many agents; Cognition argues one agent with full context is more reliable for tightly coupled work such as coding. Both are right for their task. You decide with measurements.

Part 1 runs one agent with every tool on the resolution cases, shows where it breaks, and estimates what splitting costs.

Sessions carry state between turns

An agent object is stateless and reusable; a session holds one conversation. Where the history lives is pluggable: in memory, in a file, in a vector store, or on the service side (a Foundry conversation).

session = agent.create_session()
await agent.run("My name is Ada.", session=session)
await agent.run("What is my name?", session=session)  # remembers Ada

Context providers run before each call to add context (a user profile, retrieved passages, long-term memory) and after each call to store what was learned. RAG as a context provider and RAG as a tool are the two options from Week 6, section 12.

Agents compose

MethodTurns the agent intoUse
agent.as_tool()A function tool another agent can callManager-worker without a workflow
agent.as_mcp_server()An MCP serverExpose an agent to any MCP client (Week 8)

Providers are swappable. The same Agent runs on FoundryChatClient, OpenAI, Anthropic, Ollama and others. Instructions and tools do not change; only the client does. That is how you compare models fairly.

4. Middleware: intercepting runs, model calls and tool calls

Middleware wraps a step, sees its inputs, decides whether to continue, and sees its outputs.

LayerWrapsTypical uses
Agent middlewareA whole agent.runInput screening, logging, timing, caching whole answers
Chat middlewareEach model callRedacting secrets before they leave, token budgets, swapping models
Function middlewareEach tool callAuthorization, argument validation, approvals, audit logs, rate limits per tool

A business rule the model cannot talk its way around

from agent_framework import FunctionInvocationContext, function_middleware
from app.domain import CREDIT_LIMIT


@function_middleware
async def cap_credits(context: FunctionInvocationContext, call_next) -> None:
    if context.function.name == "issue_credit" and context.arguments["amount"] > CREDIT_LIMIT:
        context.result = f"Supervisor approval required for credits above ${CREDIT_LIMIT:.0f}."
        return  # short-circuit: the tool never runs
    await call_next()  # otherwise run the tool (and any inner middleware)


billing = Agent(
    client=client,
    name="billing",
    instructions=BILLING_RULES,
    tools=[quote_fare, issue_credit],
    middleware=[cap_credits],
)

CREDIT_LIMIT is the same $25 rule used by app/domain.py and the handbook. This illustrative gate stops the tool call; it does not queue a review or issue a credit. The service's domain tool returns status="escalated" for an amount above that limit. Both are simulated action records, not a connection to a real payment system.

Prompts ask; middleware enforces. Any rule that involves money, permissions or safety belongs in code like this, with the prompt as a second line of defense. Tool approval is the built-in case of function middleware: @tool(approval_mode="always_require") pauses the run and returns the pending call in result.user_input_requests (section 7 and the lab).

5. Workflows: executors, edges, supersteps

A workflow is a directed graph. Nodes are executors: units of work that receive a typed message and may send messages on or yield output. Edges carry messages. Agents are executors too, so one graph can mix plain functions and agents.

from typing_extensions import Never
from agent_framework import Executor, WorkflowBuilder, WorkflowContext, handler


class Normalize(Executor):
    @handler
    async def run(self, case: str, ctx: WorkflowContext[str]) -> None:
        await ctx.send_message(case.strip())  # pass a str to the next executor


class Shout(Executor):
    @handler
    async def run(self, text: str, ctx: WorkflowContext[Never, str]) -> None:
        await ctx.yield_output(text.upper())  # a workflow output, not a message


normalize, shout = Normalize(id="normalize"), Shout(id="shout")
workflow = WorkflowBuilder(start_executor=normalize).add_edge(normalize, shout).build()
result = await workflow.run("  battery died  ")
print(result.get_outputs())  # ['BATTERY DIED']

Typed messagesWorkflowContext[Out, WorkflowOut] declares what an executor sends and yieldsThe graph is validated at build(): incompatible edges fail before anything runs
SuperstepsRounds: every executor with pending messages runs, then all messages are delivered at onceParallel branches are deterministic; checkpoints fall on clean boundaries
Outputs vs messagessend_message feeds the graph; yield_output produces a result for the callerOne workflow can return several outputs
Agents as executorsPass an Agent where an executor is expectedMix deterministic steps with model steps
Function executors@executor turns an async def into an executorSmall steps without a class
Functional workflows@workflow and @step write a workflow as ordinary control flowWhen a graph is more ceremony than you need

The routing decision is data (a TriageDecision object), so code can log it, test it, and refuse an impossible route before any specialist runs. That is the main advantage of routing with structured output over letting agents "decide among themselves".

7. Durable and interactive workflows: events, checkpoints, people

Events and streaming

workflow.run(input, stream=True) yields executor starts and completions, agent updates, outputs, requests for input, errors. A UI shows progress; a log records every step.

Checkpoints

With a checkpoint_storage (in memory, file, or your own) the workflow saves state at superstep boundaries. After a crash or a deploy, run(checkpoint_id=...) resumes instead of re-paying for every model call.

Human in the loop

An executor calls ctx.request_info(request, response_type); the workflow pauses. The answer comes back through run(responses={request_id: answer}) to a @response_handler.

8. The five orchestration patterns

agent_framework.orchestrations packages the common multi-agent shapes as builders that produce ordinary workflows, so they stream, checkpoint and trace like any other.

Sequential

Fixed order.

Concurrent

All at once, then aggregate.

Handoff

The active agent passes control.

Group chat

A shared conversation.

Magentic

A manager plans and re-plans.

PatternBuilderControl flowUse whenWatch out for
SequentialSequentialBuilder(participants=[a, b, c])Fixed order; each sees the conversation so farPipelines: draft, edit, checkLatency is the sum of all steps
ConcurrentConcurrentBuilder(participants=[a, b, c])All at once on the same input; results aggregatedIndependent analyses, ensembles, votingNeeds two or more participants; costs every participant every time
HandoffHandoffBuilder(...).with_start_agent(triage).add_handoff(triage, [billing, ops])The active agent transfers control through a generated handoff toolRouting decided turn by turnLoops between agents; set a termination condition. Without add_handoff, a full mesh
Group chatGroupChatBuilder(participants=[...], orchestrator_agent=..., max_rounds=...)An orchestrator picks the next speakerDebate, review, critique-revise loopsToken growth: everyone reads everything; cap the rounds
MagenticMagenticBuilder(participants=[...], manager_agent=...)A manager keeps a task ledger and a progress ledger, delegates, re-plansOpen-ended tasks without a known pathThe most calls, the least predictable; supports plan review by a person

Start with the most constrained pattern that can express the task. Sequential and concurrent are graphs you can draw before you run them. Handoff, group chat and Magentic let models choose the path: flexibility bought with predictability. In a graded service where money moves, constrained wins. Read: Orchestrations in Agent Framework.

Actions come from execution, not from prose

recording(state) captures every tool call; actions in the response are built from those records, not from what an agent says it did.

The route is reported, not inferred

route lists the agents that actually ran, so the harness and you can compare intent with behavior.

  1. ScopeOnly one agent holds issue_credit.
  2. Validate in codeThe domain checks rider and amount; middleware can cap it.
  3. Escalate by designCredits above $25 come back escalated (app/domain.py).
  4. Approve when it mattersapproval_mode="always_require".
  5. Bound the runRound limits, termination, call limits, time budgets.
  6. Record everythingEvery call is in the proof and the trace.

The writer has no tools, on purpose. The component that talks to the rider cannot take actions, so a manipulated reply cannot also move money.

11. Cost and latency of a team

latency ≈ ttriage + maxs ∈ chosen ts + twriter     tokens ≈ Σall calls (nin + nout)

Each specialist's ts includes its tool loop: one model call to decide, one per tool round, one to summarize.

Concurrency cuts latency, not cost

Fan-out to three specialists costs three specialists even when it takes the time of one.

Triage pays for itself

When it removes at least one specialist on most cases: one small classification call saves one or two full agent loops.

Context grows along chains

In sequential and group-chat patterns each agent reads everything before it; tokens grow faster than the number of agents.

Quota is shared

100,000 tokens and 100 requests per minute for every call (Week 5). A team that makes eight calls per case reaches 429 eight times sooner. Fewer, smaller calls is both the cheapest and the fastest optimization.

14. Summary

  1. Split an agent for conflicting instructions, least privilege, parallelism, context hygiene or separate evaluationand only when the measurement says it pays.
  2. Agent Framework = agents + harness agent + workflows + integrationsthe successor to Semantic Kernel and AutoGen.
  3. An agent is a client, instructions, tools, options, context providers and middleware.Sessions hold conversations; agents compose as tools and MCP servers.
  4. Middleware enforces what prompts can only requestapprovals, caps, redaction, audit.
  5. Workflows are typed graphs of executors run in supersteps.Edges express sequence, conditions, routing, fan-out and fan-in; workflows stream, checkpoint and pause for people.
  6. Five orchestrationssequential, concurrent, handoff, group chat, Magentic. Prefer the most constrained one that fits.
  7. Make routing data, report actions from execution, give side effects to one agent.
  8. Latency follows the critical path; cost follows the sum.
  9. Evaluate outcomes, actions, routes and efficiencynot just the final text.

The exercise and how it is graded

Add triage and make the money right

Service: POST /v1/resolve takes a support case and returns a resolution for the rider, the route of agents that worked on it, and the actions they took: ride credits and maintenance tickets (contract).

Starting point: every case goes to every specialist in parallel, then a writer drafts the reply. Slow, and specialists act on cases that are not theirs.

Your job: a triage agent that picks only the specialists a case needs, tighter instructions per specialist, and credits that are exactly right. 100 on the public cases is reachable: the harness names every case that missed and what your service did.

  1. Add triageTriageDecision and TRIAGE from Part 3; run it first.
  2. Build the teamOnly decision.specialists. With one, call team[0].run(case): ConcurrentBuilder needs two.
  3. Report the routeroute=["triage", *chosen, "writer"].
  4. MeasureRouting alone usually moves the score most.
  5. Make the money rightWrite the handbook's rules as a playbook, one line per situation. Per-minute charges only, never the unlock fee; credit the difference when policy reduced a fee; call issue_credit yourself, even above $25; no policy, no credit. If an amount stays wrong, compute it in code with a small tool.
  6. Route by need, report the truthA request for money needs billing even when nothing is owed; a broken bike or dock needs operations and a ticket at its station. The writer reports only actions the tools returned, with their status.

One round of a workflow: every ready executor runs, then messages are delivered together.
Fan-out, fan-in
Send one message to several executors; wait for all of them and deliver their results together.
Triage
A routing step that decides which specialists a case needs, as structured output.
Handoff
An agent transfers control of the conversation to another agent.
Magentic
A manager agent with a task ledger and a progress ledger that plans, delegates and re-plans.
Middleware
Code around an agent run, a model call or a tool call that can inspect, block or change it.
Checkpoint
Saved workflow state at a superstep boundary, so a run can resume.
Least privilege
Each agent holds only the tools its job needs.
