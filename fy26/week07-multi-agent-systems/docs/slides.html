Why this week matters

One agent with every tool works, until the prompt and the tool list grow

Confused responsibilities

One prompt holds billing rules, operations rules and tone rules. Each new rule can break another.

Too much power

Every part of the agent can issue credit, including the part answering a policy question.

Hard to debug

When a credit is wrong, which "part" of the prompt caused it?

Splitting into specialists addresses all three: each has its own instructions and only the tools it needs. It also costs more calls, more latency and more ways to fail. This week is about when to split, how to orchestrate, and how to prove the split paid off.

Three designs

Three designs, in increasing order of autonomy and cost

DesignWho decides the next stepStrengthWeakness
Single agent with toolsThe model, in one loopSimple; one context; cheapestOne long prompt; every tool always available
WorkflowYour code: a fixed graph of steps, some of them agentsPredictable, testable, auditableHandles only the paths you drew
Multi-agent systemAgents decide together: handoffs, a manager, a group chatFlexible on open-ended tasksMore calls, more latency, more ways to fail

Agent Framework's own rule: if you can write a function to handle the task, do that instead of using an agent. Use a workflow when the process has well-defined steps; use an agent when the task is open-ended.

Reasons to split, and the bill

Split for a reason you can name, and estimate the bill before you build

  • Instructions conflict. "Be concise" and "explain every clause" are different roles.
  • Least privilege. Only one role should move money.
  • Parallelism. Independent lookups can run at once.
  • Context hygiene. A specialist sees only what it needs.
  • Separate evaluation. Measure and improve each role alone.
≈ 15×tokens of a chat, for Anthropic's multi-agent research system
86%three agents, each right 95% of the time, failing independently: 0.95³

Practitioners disagree, and both sides are right for their task. Anthropic wins on broad research with many agents; Cognition argues one agent with full context is more reliable for tightly coupled work. You decide with measurements.

Middleware

Prompts ask. Middleware enforces

LayerWrapsTypical uses
AgentA whole agent.runInput screening, logging, timing
ChatEach model callRedact secrets, token budgets, swap models
FunctionEach tool callAuthorization, validation, approvals, audit

Any rule that involves money, permissions or safety belongs in code, with the prompt as a second line of defense. Tool approval is the built-in case of function middleware.

A business rule the model cannot talk around

from app.domain import CREDIT_LIMIT

@function_middleware
async def cap_credits(context: FunctionInvocationContext,
                      call_next) -> None:
    if (context.function.name == "issue_credit"
            and context.arguments["amount"] > CREDIT_LIMIT):
        context.result = "Supervisor approval required above $25."
        return                 # short-circuit: the tool never runs
    await call_next()          # otherwise run the tool

The $25 limit comes from the domain code. This gate stops a call; it does not issue a credit or queue a real review.

Part 2 · Lab Part 2

Workflows: you fix the order, agents fill the steps

Most production systems are workflows with agents inside them.

Workflows

A workflow is a typed graph: executors are nodes, edges carry messages

class Normalize(Executor):
    @handler
    async def run(self, case: str, ctx: WorkflowContext[str]) -> None:
        await ctx.send_message(case.strip())    # to the next executor

class Shout(Executor):
    @handler
    async def run(self, text: str, ctx: WorkflowContext[Never, str]) -> None:
        await ctx.yield_output(text.upper())    # a result for the caller

normalize, shout = Normalize(id="normalize"), Shout(id="shout")
workflow = (WorkflowBuilder(start_executor=normalize)
            .add_edge(normalize, shout).build())
result = await workflow.run("  battery died  ")
print(result.get_outputs())                     # ['BATTERY DIED']
ConceptWhy it matters
Typed messagesThe graph is validated at build(): incompatible edges fail before anything runs
SuperstepsRounds: every ready executor runs, then messages are delivered together. Parallel branches stay deterministic
Messages vs outputssend_message feeds the graph; yield_output answers the caller
Agents as executorsMix deterministic steps with model steps
Workflow as agentworkflow.as_agent(): a team usable wherever one agent is

Lab Part 2

Concurrent runs take the time of the slowest agent, not the sum

money = Agent(client=client, name="money",
              instructions="List only what the rider may be owed, with amounts.",
              tools=[search_handbook, quote_fare])
fleet = Agent(client=client, name="fleet",
              instructions="List only what the operations team must do.",
              tools=[get_station])

team = ConcurrentBuilder(participants=[money, fleet]).build()
outputs = (await team.run(CASE)).get_outputs()

Notice the tools: money can price rides but cannot open tickets; fleet can read stations but cannot touch money. Least privilege for agents, the same principle as the managed identity in Week 5.

8.9 sfor both agents on the lab's battery case, one run on the course sandbox. Each runs its own tool loop.

Concurrency cuts latency, not cost

Two agents in parallel still pay for two agents. Sequential pays the sum of both latencies.

Durable and interactive

Real processes pause, fail, and wait for people

Events

workflow.run(input, stream=True) yields executor starts and ends, agent updates, outputs, requests and errors. A UI shows progress; a log records every step.

Checkpoints

With checkpoint_storage the workflow saves state at superstep boundaries. After a crash, run(checkpoint_id=...) resumes instead of re-paying for every model call.

People in the loop

An executor calls ctx.request_info(...); the workflow pauses until run(responses={...}) brings the answer: a supervisor approves a $60 credit.

Orchestrations

Five orchestrations, from the most constrained to the most autonomous

Sequential

SequentialBuilder
Fixed order. Draft, edit, check.
Cost: latency is the sum.

Concurrent

ConcurrentBuilder
All at once, then aggregate.
Cost: every participant, every time.

Handoff

HandoffBuilder
The active agent passes control.
Watch: ping-pong; set termination.

Group chat

GroupChatBuilder
A shared conversation; debate, critique.
Watch: everyone reads everything.

Magentic

MagenticBuilder
A manager plans, delegates, re-plans.
Watch: most calls, least predictable.

Rule of thumb: start with the most constrained pattern that can express the task. In a graded service where money moves, constrained wins. At the far end, GPT-5.6 can spawn its own subagents inside one Responses call (multi_agent, preview): the least code and the least control. Read Orchestrations in Agent Framework.

The resolution team: route with data, approve in code, measure

A triage decision your code can log and test, an approval your code controls, and a team judged by its actions and its latency, case by case.

Actions come from execution. recording(state) captures every tool call; actions are built from it, not from what an agent says.

The route is reported, not inferred. route lists the agents that ran, so you can compare intent with behavior.

Routing

Make routing a decision your code can log, test and enforce

class TriageDecision(BaseModel):
    specialists: list[Literal["policy", "billing", "operations"]]
    reason: str

triage = Agent(client=client, name="triage", instructions=TRIAGE)
decision = (await triage.run(case,
    options={"response_format": TriageDecision})).value

The writer has no tools, on purpose: the component that talks to the rider cannot take actions, so a manipulated reply cannot also move money.

Human in the loop

A tool can pause the run until a person approves

@tool(name="issue_credit", approval_mode="always_require")
def issue_credit_with_approval(rider_id: str, amount: float, reason: str) -> dict:
    """Give a rider ride credit in US dollars. A person approves every credit."""
    return domain.issue_credit(rider_id, amount, reason)

session = cashier.create_session()
result = await cashier.run(CASE, session=session)      # pauses here

decisions = []
for request in result.user_input_requests:
    arguments = json.loads(request.function_call.arguments)
    approved = arguments["amount"] <= 25               # a person decides
    decisions.append(Message(role="user",
        contents=[request.to_function_approval_response(approved)]))
final = await cashier.run(decisions, session=session)   # resumes

Cost and latency

Latency follows the critical path. Cost follows the sum

Latency

ttriage + max(tchosen specialists) + twriter

Tokens

Σ over every call (input + output)

Each specialist's time includes its own tool loop: decide, call, summarize.

  • Concurrency cuts latency, not cost. Three specialists cost three, even when they take the time of one.
  • Triage pays for itself when it removes at least one specialist on most cases.
  • Context grows along chains. In sequential and group-chat patterns each agent reads everything before it.
  • Quota is shared. 100,000 tokens and 100 requests a minute for every call. A team that makes eight calls per case reaches 429 eight times sooner. Your service answers 503 with Retry-After; the harness waits.

Summary

What to remember

  • Start with one agent. Split for conflicting instructions, least privilege, parallelism, context hygiene or separate evaluation, and only when the measurement says it pays.
  • Workflows fix the order; agents choose it. Prefer the most constrained orchestration that fits.
  • Make routing data: structured triage your code can log and test.
  • Middleware enforces what prompts can only request. Give side effects to one agent; approve the ones that are hard to undo.
  • Report actions from execution, not from prose.
  • Latency follows the critical path; cost follows the sum.
  • Judge a team by its actions and its latency, case by case.
