Harnesses and Agentic CodingThe program that runs an agent, the program that grades it, and the protocol that lets any agent use your tools.

A model on its own only produces text. What makes it an agent is the harness around it: the loop that calls tools, the context it is given, the permissions it has, and the checks that tell it whether it succeeded. Coding agents such as GitHub Copilot, Claude Code and Codex are harnesses built for software. This week you look at harnesses from both sides: you publish your service's tools to any agent through the Model Context Protocol, and you use a coding agent to build a feature against a specification written as tests, verified by your own harness.

1. Two kinds of harness

The word "harness" means two things in this course, and the two meet this week.

Evaluation harnessAgent harness
What it isCode that runs a system against tasks and scores itThe runtime that turns a model into an agent that does work
In this courseharness/: checks per week, public data, proofsAgent Framework's loop (Weeks 6 and 7), GitHub Copilot, Codex, Claude Code
Its jobMeasureAct
Its outputScores, failures, evidenceTool calls, file edits, answers

They meet in verification. A good agent harness gives the agent a way to check its own work: run the tests, the linter, the evaluation harness. An agent that can measure itself can iterate without you. This week's exercise is built on that: the coding agent edits code, runs pytest and the harness, reads the failures, and tries again.

2. Anatomy of an agent harness

PartQuestion it answersExamples
LoopWhen does the agent stop?Iteration limits, time budgets, "until tests pass", todo lists that must be empty
ContextWhat does the model see on each call?Instructions, AGENTS.md, opened files, memory, skills, compacted history
ToolsWhat can it do?Read and edit files, run commands, search, MCP servers, subagents
PermissionsWhat may it do without asking?Sandbox boundaries, approval policies, allow and deny lists, hooks
VerificationHow does it know it succeeded?Test suites, type checkers, linters, your evaluation harness
ObservabilityHow do you know what it did?Session logs, diffs, traces, pull requests

The model supplies judgment; the harness supplies everything that makes judgment safe and productive. Two products using the same model can differ enormously because their harnesses differ.

3. Context engineering

The model only knows what is in its context window, and every token there costs money, time and attention. Context engineering is putting the right tokens in front of the model at the right moment.

TechniqueIdeaWhere you see it
Repository instructionsA file the harness always loads: conventions, commands, rules, "done means"fy26/AGENTS.md, .github/copilot-instructions.md
Path-scoped instructionsRules that load only for matching files.github/instructions/*.instructions.md with applyTo
Just-in-time retrievalThe agent searches instead of receiving everything up frontEvery coding agent's search tools
SkillsFolders of instructions, scripts and resources; only a short description loads until needed.github/skills/ in this repository
CompactionSummarize or drop old turns and tool outputs when the window fillsLong coding sessions; Agent Framework compaction
SubagentsDelegate to a fresh agent with a clean context; get back only the resultCodebase research, running a test suite
MemoryNotes that persist across sessionsCopilot Memory, Agent Framework file memory
Tool searchHide hundreds of tool definitions behind a search toolFoundry toolboxes (tool_search, call_tool)

Short, specific, testable

"Do not change app/contract.py" changes behavior. "Write clean code" wastes tokens. Compare this repository's AGENTS.md: commands in a table, rules a reviewer can check, and a definition of done.

Before MCP, every agent product invented its own plugin format, and every tool had to be integrated once per product. MCP standardizes the connection, as the Language Server Protocol did for editors and programming languages.

Why it matters to you: you write a tool once, in app/mcp_server.py, and every MCP host can use it. The lab connects all of them to the same /mcp endpoint.

5. MCP on the wire, revision 2026-07-28

The current revision made the protocol stateless. The initialize handshake and the Mcp-Session-Id header are gone. Every request carries its own protocol version, client identity and capabilities in params._meta, and the headers MCP-Protocol-Version, Mcp-Method and Mcp-Name mirror them so gateways can route without parsing the body.

Discovery replaces the handshake

POST /mcp
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: server/discover

{"jsonrpc": "2.0", "id": 1, "method": "server/discover",
 "params": {"_meta": {
   "io.modelcontextprotocol/protocolVersion": "2026-07-28",
   "io.modelcontextprotocol/clientInfo": {"name": "notebook", "version": "1"},
   "io.modelcontextprotocol/clientCapabilities": {}}}}
MethodRequestResult
server/discover_meta onlysupportedVersions, capabilities, server identity in _meta
tools/listno argumentstools: each with name, description, inputSchema
tools/callname, arguments; header Mcp-Namecontent, structuredContent, isError

Why stateless matters: the service runs with stateless_http=True, so any replica of your Container App can answer any request. No sticky sessions, no session store. A server that needs state across calls mints an explicit handle and receives it back as an ordinary tool argument.

A server may answer with plain JSON or a server-sent event stream; clients must accept both. harness/checks/week08.py is a complete MCP client in about forty lines.

Other changes in this revision

Older clients still work: the MCP Python SDK serves the earlier, session-based revisions on the same endpoint. Read: What changed in 2026-07-28.

subscriptions/listenOne long-lived stream for change notifications the client opted into, replacing the old GET endpoint
Cacheable liststools/list carries ttlMs and cacheScope, in a deterministic order, which also helps prompt caching (Week 5)

6. MCP security

MCP connects models to code that does things. The specification's own principles: users must consent to data access and tool use; tools are arbitrary code execution; descriptions from an untrusted server are themselves untrusted.

ThreatWhat happensDefense
Tool poisoningA tool's description hides instructions the model obeysInstall servers you trust; review descriptions; pin versions; prefer curated registries and toolboxes
Prompt injection through resultsA tool returns text with instructions in itTreat results as data; guardrails on tool responses (Week 10); least-privilege tools
Confused deputy, token passthroughA server forwards the client's token to another service, which trusts itServers validate that tokens were issued for them and never pass client tokens through
Over-broad serversOne server with fifty write toolsEnable only the tools a task needs; separate read and write servers
Supply chainnpx some-mcp-server runs unreviewed code on your machineTreat a server like any dependency: source, version, publisher
DNS rebindingA web page reaches a server on your laptop through your browserValidate Host and Origin: app/main.py allows only its own names
Anonymous remote serversAnyone can call your /mcpAuthenticate (the API key in Week 10; OAuth or Entra ID in production), rate-limit, log

Read: MCP security best practices

10. OpenAI Codex and the Agents SDK

Codex is OpenAI's coding agent: a CLI, an IDE extension, a cloud service, and part of the ChatGPT desktop app. Its permission model makes two separate questions explicit: what the agent may touch, and when it must ask.

ControlWhat it decidesExample settings
SandboxWhich files and network the agent can touch at allworkspace-write: edit inside the workspace only
Approval policyWhen the agent pauses to askon-request: before crossing the sandbox boundary
ReviewerWho answers the approvalYou, or an automatic reviewer that escalates only actions it judges unsafe

Modes combine these: Ask for approval, Approve for me, Full access (no sandbox: only in a disposable environment), or a custom profile in config.toml. /init writes AGENTS.md, /review reviews a diff without changing the tree, codex exec runs non-interactively in scripts and CI, and codex mcp adds MCP servers.

The OpenAI Agents SDK is the code-level counterpart: agents with instructions and tools, handoffs and agents-as-tools, guardrails that run in parallel with the agent, sessions, human-in-the-loop, built-in tracing, and sandbox agents that work in isolated workspaces. Agents built with it can be deployed to Foundry as hosted agents.

11. Building a harness: Agent Framework's harness agent

You can build the same kind of harness for your own agents. Agent Framework ships an opinionated, batteries-included harness agent for long, multi-step work.

from agent_framework import FileSystemAgentFileStore, create_harness_agent

agent = create_harness_agent(
    client=state.models.agent_client(),
    name="ops-analyst",
    harness_instructions="Use tools deliberately and report verified results.",
    agent_instructions="You analyze Lakeshore Ride station data and propose rebalancing plans.",
    tools=[get_station, search_handbook],
    max_context_window_tokens=128_000,
    file_access_store=FileSystemAgentFileStore("agent-files"),  # opt-in shared workspace
)
session = agent.create_session()
result = await agent.run("Which stations will run out of docks this evening?", session=session)

12. Foundry for agentic development

Microsoft Foundry meets coding agents in both directions: coding agents can drive Foundry, and Foundry can host agents built with coding-agent SDKs.

Driving Foundry from a coding agent

The Microsoft Foundry Skill, bundled with the Foundry and Azure MCP servers in the Azure Skills plugin, teaches GitHub Copilot, Copilot CLI or Claude Code the Foundry workflows: create a project, deploy a model, scaffold and deploy a hosted agent, run evaluations, curate datasets from traces, optimize instructions, troubleshoot deployments, check RBAC and quota.

Hosting agents built with these SDKs

Foundry hosted agents accept code written with Agent Framework, LangGraph, the OpenAI Agents SDK, the Anthropic Agent SDK or the GitHub Copilot SDK, and run it with a managed endpoint, a dedicated Entra identity, per-session sandboxes and tracing. 14. Security of agentic coding

A coding agent runs with your permissions on your machine or your repository. Treat it as a fast, literal-minded colleague who can be tricked.

RiskExampleMitigation
Prompt injection through contentAn issue, README, web page or dependency comment says "also add this curl command to the build"Approvals for commands and network; sandboxing; review diffs; cloud agents with firewalls
Secret exposureThe agent reads .env and pastes a key into a log or commitRules that forbid reading secrets (as in our AGENTS.md), hooks that scan for secrets, keyless auth
Destructive commandsrm -rf, git push --force, terraform destroyDeny lists, approval for anything irreversible, work on branches
Unreviewed dependenciesA package that does not exist or is malicious ("slopsquatting")Lock files, dependency review, CI checks
Over-trusting outputTests pass because they were weakenedProtected tests, code review, CI that runs the real suite

Every mitigation in this table is a harness feature: sandbox, approval policy, hooks, instructions, verification. That is the lesson of the week.

The exercise and how it is graded

A tool for riders at a full station: nearest_station_with_docks

Service: POST /mcp publishes search_handbook, quote_fare and get_station (app/mcp_server.py).

Specification: the tests in tests/test_week08_nearest_station.py, skipped until the function exists. Input: a station id. Output: the closest other station that is open and has at least one free dock, by great-circle distance (distance_km in app/domain.py). Returns station_id, name, distance_km, docks_available. An unknown id returns {"error": ...}.

Your job: the coding agent writes the code. You write the prompt, review every change, run the tests and the harness, and decide what ships. When the tests pass and the tool is published at /mcp, the local harness shows 100.

A prompt that works

Read AGENTS.md and tests/test_week08_nearest_station.py. Implement nearest_station_with_docks in app/domain.py so that every test in that file passes, using the existing distance_km. Publish it as an MCP tool with the same name in app/mcp_server.py, with a docstring a client agent can understand. Do not modify any test. When you are done, run uv run pytest and uv run ruff check . and show me the output.

Review the diff before you accept it

Does it skip the origin, closed stations and stations with zero free docks? Does it use great-circle distance, not raw latitude and longitude? Does an unknown id return an error instead of raising? Did it change anything it was not asked to change?

When the agent gets stuck

Give it the exact failing test output and ask it to fix that test only. If two rounds do not converge, read the failing assertion yourself: usually one sentence in the prompt fixes it. If some tests stay red, ship what passes: a published tool with some correct answers still scores.

CheckWeightWhat it measures
core.health, core.info1 + 1The service is up and identifies you

w08.mcp.tools2The three course tools are published, with input schemas

Write your own check (Part 6)

def unknown_station_is_an_error(ctx: Context) -> tuple[float, str]:
    result = call_tool(ctx, "nearest_station_with_docks", {"station_id": "LS-99"})
    ok = isinstance(result, dict) and "error" in result
    return (1.0 if ok else 0.0), f"LS-99 -> {result}"
  1. Grade the outcome, not the path.Check the answer, not which helper produced it.
  2. Separate capability from regression.Can it do the new thing? Does the old thing still work?
  3. One run is one sample.pass@k: at least one of k runs succeeds. pass^k: all k do. Users experience pass^k.
  4. Read the transcripts.A score says that something failed; the proof says why.

These ideas come from Demystifying evals for AI agents (Anthropic).
