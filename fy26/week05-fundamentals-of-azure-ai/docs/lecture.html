Four questions, and what you will be able to do

Four questions sit behind every model call. By the end of the session each has a concrete answer in your own service, running in Azure and scored by the harness.

Where does the model live?

A Foundry resource, a project, a deployment you call by name. Sections 1 to 4.

Who may call it?

An Entra ID token and a role. No API keys, anywhere. Section 5.

What does it cost?

Tokens in, tokens out, reasoning tokens; time to first word. Sections 6 and 7.

Can code trust the answer?

A schema the API enforces, and instructions improved by measurement. Sections 8 and 9.

Foundry resource

Microsoft.CognitiveServices/accounts, kind AIServices. The security and billing boundary: networking, managed identity, local authentication on or off, deployments and their quota.

Project

A workspace inside the resource for one application or team. Agents, files, evaluations, connections and traces live here. Access can be granted per project.

Deployment

A named instance of one model version, with a deployment type and a capacity. Your code calls the deployment name. Pointing an existing name at a newer model version upgrades without touching code.

Endpoints

One resource exposes two families of URLs: an OpenAI-compatible v1 endpoint and a project endpoint.

EndpointShapeUsed by
OpenAI-compatible v1https://<resource>.openai.azure.com/openai/v1/Any OpenAI SDK: Responses, embeddings. Our app/models.py

Why local_auth_enabled = false? An API key is a bearer secret: whoever holds it is you, it does not expire on its own, and it ends up in notebooks, screenshots and git history. With keys disabled, every caller must present an Entra ID token, so access is per identity, auditable and revocable. Section 5 shows how.

3. Choosing a model

There is no best model, only the best model for a task at a price. Compare candidates on these dimensions.

DimensionQuestion to askWhy it matters here
CapabilityDoes it do the task: structured output, tool calling, vision, audio?Triage needs structured output; Week 6 needs tool calling
Size tierFlagship, mini or nano?Smaller is faster and cheaper, and often enough for classification
ReasoningDoes it think before it answers, and can you set the effort?Better on multi-step problems; costs reasoning tokens and time
Context windowHow many tokens fit in one request?Long documents, long conversations, many tools
PriceInput, cached input and output are priced separatelyOutput tokens usually cost several times more than input
AvailabilityWhich regions and deployment types?Data residency and quota
LifecycleWhen does this version retire?You will have to upgrade, and re-evaluate

A rule that saves money: start with the smallest model that passes your harness. Move up a tier only when a measured failure requires it, and keep the measurement.

The catalog in October 2026

Foundry sells OpenAI's newest series directly: GPT-6.1 and GPT-6 (gpt-6.1-sol, gpt-6-astra, gpt-6-sol, gpt-6-luna), GPT-5.6 (gpt-5.6-sol, -terra, -luna), GPT-5.5, and the GPT-5.4 tiers (gpt-5.4-pro, gpt-5.4, gpt-5.4-mini, gpt-5.4-nano), next to open-weight gpt-oss and models from other providers. This course runs on gpt-5.4-mini (version 2026-03-17): it has everything the service needs (Responses API, structured outputs, parallel tool calls, reasoning effort), a 400,000-token context window, and a price that lets every student run the harness many times. The newest flagship is not the right default for picking one of six labels; it is a candidate to measure when a failure calls for it. See Foundry Models sold directly by Azure.

Reasoning, lifecycle and routing

  • Reasoning models such as the GPT-5 family generate hidden reasoning before the visible answer. You set how much with reasoning={"effort": ...}, from none upward. More effort helps on multi-step problems (pricing rules with exceptions, plans, code) and wastes time on simple ones (picking one of six categories). Section 7 shows a measurement.
  • Lifecycle. Every model version has a retirement date. In production, pin the version, evaluate the successor against your harness, then switch. See model retirements.
  • Model router. One deployment that picks a model per request based on difficulty. It trades predictability for cost: try it, and measure whether accuracy holds.

Data at rest stays in your resource's geography for every type; the table is about where inference runs. Global Standard also offers request-level tiers: flex (cheaper, delay-tolerant) and priority (faster).

Quota, as arithmetic

Standard deployments have two limits that come from one number: tokens per minute (TPM) and requests per minute (RPM). In Terraform, capacity is in thousands of TPM, so capacity = 100 gives 100,000 TPM and, for gpt-5.4-mini, 100 RPM (the deep dive reads both from your deployment). Quota is granted per subscription, region and model, and you split it among deployments.

100,000 / 100tokens and requests per minute on your gpt-5.4-mini deployment (capacity = 100)
100, not 140triage calls a minute: tokens alone would allow 100,000 / 700, but the request limit binds first
1,000tokens per call where the two limits meet: below it requests bind first, above it tokens do

The starting triage call measures about 170 input and 40 output tokens; with the rules you write in the lab it grows to roughly 700. Either way the request limit stops you at 100 calls a minute. A Week 7 case that makes eight model calls, each with a longer context, uses both budgets eight times faster. That is why multi-agent systems hit limits first.

Throttling

Caller
→
Your service
→
Foundry over quota429, Retry-After
→

Over the limit, Foundry answers HTTP 429 with a Retry-After header. A well-behaved client waits that long, retries with exponential backoff and jitter, and gives up after a few attempts. Our app/middleware.py turns an upstream 429 into 503 with Retry-After, so callers know the problem is temporary capacity, not their request.

Provisioned throughput buys reserved capacity at a fixed hourly price. It pays off when traffic is high and steady, or when latency variance matters. Below that, pay-per-token is cheaper. See provisioned throughput and deployment types.

5. Identity: keyless by design

Your code never holds a secret. It asks for a short-lived token, and Foundry checks both the token and the role of whoever presents it.

  • DefaultAzureCredential tries a chain of identity sources and uses the first that works: environment variables, workload identity, managed identity, then developer tools such as the Azure CLI.
  • Token audience. The token is issued for https://ai.azure.com/.default. A token for another service, such as Storage, is rejected.
  • Authorization is RBAC. A valid token is not enough; the identity needs a role on the resource.
Role (previous name)Can doWho has it here
Foundry User (Azure AI User)Call models, use agents and project data: the data planeYou, and your Container App's managed identity
Foundry Project Manager (Azure AI Project Manager)Manage a project and assign Foundry User within itNobody in this course
Foundry Owner (Azure AI Owner)Full access to projects and resourcesNobody
Foundry Account Owner (Azure AI Account Owner)Manage the resource: deployments, guardrails, connectionsYou have these rights as subscription Owner

Control plane versus data plane. Creating a deployment or changing a guardrail goes through Azure Resource Manager (control plane). Calling a model is the data plane. The running service needs only the data plane, so its identity gets only Foundry User: if it is compromised, it cannot create deployments or change safety settings. See infra/identity.tf and RBAC for Microsoft Foundry.

Agents get identities too. Foundry agents receive their own Entra agent identity, so a tool call is authorized as the agent, not as a shared key. Week 10 returns to this.

Part 2 builds the client exactly as FoundryModels.__init__ in app/models.py does: get_bearer_token_provider(DefaultAzureCredential(), TOKEN_SCOPE). There is no key anywhere in the repository, by design.

from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import OpenAI

token = get_bearer_token_provider(DefaultAzureCredential(), "https://ai.azure.com/.default")
client = OpenAI(base_url=FOUNDRY_OPENAI_ENDPOINT, api_key=token)  # api_key accepts a token provider

r = client.responses.create(
    model="gpt-5.4-mini",  # the deployment name
    instructions="You are Lakeshore Ride support. One sentence.",
    input="Can I end my ride at any station?",
    reasoning={"effort": "low"},
)
print(r.output_text)
print(r.usage.input_tokens, r.usage.output_tokens, r.usage.output_tokens_details.reasoning_tokens)

Instructions versus input

Instructions say who the model is: you write them, they are stable, they are trusted. Input is what the user said: it changes every request and is never trusted. Keeping them apart matters for caching (section 7) and for security (Week 10).

Output items, not one string

A response is a list of typed items: message, reasoning, function_call, and built-in tool outputs. output_text joins the text for you. In Week 6 you read function_call items yourself.

Conversation state

The model is stateless; every call stands alone. There are three ways to carry a conversation:

ApproachHowTrade-off
Client-side historyResend all previous messages as inputFull control, nothing stored server-side; you manage truncation
previous_response_idPoint at the last response; the service chains the historySimple; requires store=True (the default)
Conversations APIA durable conversation object that responses attach toShared across clients and channels; what Foundry agents use

Server-side state does not make history free. The whole history is still processed as input tokens on every turn. Long conversations get slower and more expensive until you summarize or truncate them.

Streaming, and why Responses

With stream=True the API sends events as the response is produced: response.created, many response.output_text.delta, then response.completed. The total time does not change; the time to the first visible word does. For a chat interface that is the difference between "fast" and "broken"; for a JSON API such as /v1/classify it buys nothing.

Chat Completions is still supported, but the Responses API models what agents need: typed items, server-side state, built-in tools, and reasoning that persists across turns. New platform features, Foundry agents included, are built on it. The older Assistants API (threads and runs) is replaced by Responses plus Conversations.

7. Tokens, cost and latency

A token is a piece of a word, about four characters of English. You pay per token, with separate prices for input, cached input and output. Reasoning tokens are billed as output.

cost = (ninput − ncached)·pinput + ncached·pcached + noutput·poutput

Here ninput is usage.input_tokens, ncached is usage.input_tokens_details.cached_tokens, and noutput is usage.output_tokens. These are totals with nested breakdowns: cached tokens are already part of input, and reasoning tokens are already part of output. Do not add either breakdown again. The p values are prices per token; divide by 1,000,000 if your price table quotes prices per million tokens. Tool and hosting charges are separate. See reasoning token usage and prompt caching.

latency ≈ time to first token (queue, prompt processing, reasoning) + nvisible output / tokens per second
LeverEffect on costEffect on latency
Shorter output: one sentence, a JSON object, a labelLarge: output is the expensive sideLarge: fewer tokens to generate
Lower reasoning effortFewer reasoning tokensShorter time to first token
Smaller model tierLower price per tokenUsually faster
Stable prefix first, so it is cachedCached input is discountedFaster prompt processing
Fewer calls per request (Week 7)LinearLinear on the critical path

Reasoning effort, measured

"A member rides an e-bike for 40 minutes at $0.18 a minute. What do they pay?" Every effort level answered $7.20. Only the hidden reasoning changed:

none (default)0 tokens
low25 tokens
medium25 tokens
high40 tokens
xhigh72 tokens

On an easy question, more effort buys nothing but tokens and time. On a rule with exceptions it may buy correctness. Measure on your task before you choose.

Prompt caching, measured

When the first 1,024 or more tokens of a request match a recent request, they are served from cache: cheaper and faster, with no code change. With the whole handbook in the instructions and three different questions:

QuestionInput tokensCached tokens
Can I bring my dog on a bike?1,7410
How long is a day pass valid?1,7401,280
Is there a student plan?1,7381,280

The rule that follows: put stable content (instructions, tool definitions, examples) first and the variable part (the user's message) last. Never put a timestamp or request id at the top. The lab reads usage.input_tokens_details.cached_tokens.

8. Structured output: from prose to contracts

A service cannot parse prose. There are three levels of "please answer in JSON", and only one gives a guarantee your code can rely on.

LevelWhat the API guaranteesFailure mode
Ask in the promptNothingSometimes prose, sometimes invalid JSON, sometimes the wrong fields
JSON modeValid JSONAny shape: missing fields, invented values
Structured outputs (strict JSON Schema)Valid JSON that matches your schemaThe model can still refuse, or choose a wrong but valid value

With structured outputs the schema constrains generation itself: the model cannot produce a token that would break it. You describe the schema with Pydantic and the SDK converts it.

from typing import Literal
from pydantic import BaseModel, Field


class TicketLabel(BaseModel):  # the real one is in app/contract.py
    category: Literal["billing", "bike_issue", "station_issue", "account", "safety", "other"]
    urgency: Literal["low", "medium", "high"]
    summary: str = Field(description="One sentence, at most 25 words.")


parsed = client.responses.parse(model=MODEL, instructions=RULES, input=ticket, text_format=TicketLabel)
label: TicketLabel = parsed.output_parsed
  1. Literal removes invention.An enum in the schema means the model cannot create a seventh category.
  2. Field descriptions are prompt.The model reads description=...; write it as an instruction.
  3. Shape is guaranteed; judgment is not.Is a stuck dock station_issue or bike_issue? The schema cannot know. Your instructions must say.
  4. Validate at the boundary anyway.Refusals and truncated outputs happen. FoundryModels.parse retries once, then fails loudly; FastAPI validates the response model again before it leaves the service.

A description is not a validator. “At most 25 words” is a writing instruction for the model, not a Pydantic length constraint. Keep that concise target; the public schema check separately requires a non-empty summary of at most 300 characters. A valid shape does not prove that the category, urgency or summary is useful.

9. Prompts as code, improved by measurement

Instructions are code. They live in git, they have bugs, and they need tests.

Part of good instructionsExample for triage
Role and task"You triage Lakeshore Ride support tickets."
DefinitionsOne line per category, with typical cases
RulesWhen urgency is high, medium or low, stated so a person could apply them
Tie-breakers"Safety beats everything. A refund request is billing, even if a broken bike caused it."
Output constraintsLength of the summary; no personal data
Examples (few-shot)Three or four short tickets with labels, chosen for the hard cases
  1. Run the harnessScore the current instructions.
  2. Read the missesNot the score: which tickets, which labels, why.
  3. Form a hypothesisWhich rule would a new support agent need?
  4. Change one thingThen run the harness again.

One change at a time

Otherwise you will not know what helped.

Know your noise

The same prompt can move a point or two between runs. One point is noise; five points is signal.

Do not overfit

Grading uses tickets you have not seen. A rule that names a public ticket's words is an answer, not a rule.

This loop (measure, read failures, change, measure) is the core skill of the course. Week 10 scales it with evaluators and LLM judges.

10.4 A prompt agent in code

from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import CodeInterpreterTool, PromptAgentDefinition
from azure.identity import DefaultAzureCredential

project = AIProjectClient(endpoint=FOUNDRY_PROJECT_ENDPOINT, credential=DefaultAzureCredential())

agent = project.agents.create_version(  # every call creates a new immutable version
    agent_name="lakeshore-fare-helper",
    definition=PromptAgentDefinition(
        model="gpt-5.4-mini",
        instructions="You answer Lakeshore Ride fare questions. Use Python for any arithmetic.",
        tools=[CodeInterpreterTool()],  # a built-in tool: Foundry runs the code in a sandbox
    ),
)

openai = project.get_openai_client()  # the same OpenAI SDK, against the project
conversation = openai.conversations.create()
reply = openai.responses.create(
    conversation=conversation.id,
    input="Three 25-minute e-bike rides at $0.40 a minute plus a $1 unlock each: total?",
    extra_body={"agent_reference": {"name": agent.name, "type": "agent_reference"}},
)
print(reply.output_text)

The agent now exists in your project: find it under Agents in the Foundry portal, chat with it in the playground and read its traces. Nothing ran on your laptop except the HTTP calls.

11. Safety from the first call

Every model deployment has a guardrail from the moment it exists. By default it is Microsoft.DefaultV2: Azure AI Content Safety classifiers check input and output for hate, sexual content, violence and self-harm, and detect user prompt attacks. The exercise and how it is graded

Triage that generalizes

Service: POST /v1/classify labels a rider's message with a category, an urgency and a summary (contract). POST /v1/chat answers free text.

Starting point: app/services/classify.py only tells the model the category names. It scores in the 80s.

Your job: write instructions that define each category and the urgency rules; measure; iterate; deploy. 100 on the public data is reachable: every miss in the report points to a rule you can write. Write rules that generalize, never answers: grading uses tickets you have not seen.

Deploy and submit

  1. Buildaz acr build sends app/ to your registry and builds the image in Azure. No Docker on your laptop.
  2. Roll outThe new tag goes to infra/image.auto.tfvars; terraform apply creates a new revision.
  3. WaitThe old revision serves until the new one answers /v1/info with the new version.
  4. Scorecourse.check(5, url) runs the harness against the live URL and saves a proof in reports/.
url = course.deploy()          # build the image in Azure, roll out a new revision
proof = course.check(5, url)   # score the live URL with the Week 5 harness

The deep dive: optional, after you submit

The lab uses each idea once, to ship a service. The deep dive returns to sections 2 to 11 and looks underneath: your resource from the control plane, a token on the wire, quota and retries, reasoning effort measured, and an agent in Foundry Agent Service.

Lab: required

lab.ipynb changes your service in app/ and deploys it. The harness grades that deployed URL, and nothing else.

Deep dive: optional

deep-dive.ipynb runs the lecture's ideas as code you can change. It is not graded. It does not edit app/ or deploy, so it cannot change your score.

Before you open it

  • When. After you have deployed and submitted your URL. The deep dive cannot raise your score, so do not let it take time from the lab.
  • What it needs. The same as the lab: Setup complete, the fy26/.env file that the setup notebook writes, and az login. Open it in VS Code with the fy26/.venv kernel.
  • How to run it. Run the setup cell, then the parts in order. Later parts reuse the client and helpers defined in earlier ones, so a part run on its own can fail with a NameError. You can stop after any part.
  • Cost and side effects. A few cents of model calls. Part 7 creates an agent in your Foundry project and deletes it at the end of the part.

Words used here

Deployment
A named instance of one model version with a type and a capacity. Code calls its name.
TPM
Tokens per minute: the quota unit of a standard deployment. capacity is in thousands of TPM.
RPM
Requests per minute: the second limit set by the same capacity. Short calls hit it first.
PTU
Provisioned throughput unit: reserved model capacity billed by the hour.
Entra ID token
A short-lived credential issued for one audience, here https://ai.azure.com/.default.
Managed identity
An identity Azure gives a resource, such as your Container App, with no secret to store.
Control plane, data plane
Managing resources versus using them. The service needs only the data plane.
Reasoning tokens
Hidden tokens a reasoning model generates before answering; billed as output.
Cached tokens
Input tokens served from the prompt cache because the prefix matched a recent request.
Structured outputs
Generation constrained by a strict JSON Schema, so the result always parses.
Guardrail
A named set of safety controls on a deployment or agent; the default is Microsoft.DefaultV2.
