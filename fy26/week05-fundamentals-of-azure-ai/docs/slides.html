Why this week matters

Four questions sit behind every model call

Where does the model live?

A Foundry resource, a project, a deployment you call by name.

Who may call it?

An Entra ID token and a role. No API keys, anywhere.

What does it cost?

Tokens in, tokens out, reasoning tokens. Time to first word.

Can code trust the answer?

A schema the API enforces, and instructions improved by measurement.

By the end of the session each question has a concrete answer in your own service, running in Azure and scored by the harness.

One line of Terraform

API keys are switched off, on purpose

infra/foundry.tf

resource "azurerm_cognitive_account" "foundry" {
  kind                       = "AIServices"
  project_management_enabled = true
  local_auth_enabled         = false  # no keys at all
}

A key is a bearer secret

Whoever holds it is you. It does not expire on its own, and it ends up in notebooks, screenshots and git history.

A token is an identity

Every caller presents a Microsoft Entra ID token. Access is per identity, auditable, and revocable.

Choosing a model

There is no best model, only the best model for a task, at a price

DimensionQuestion to ask
CapabilityStructured output? Tool calling? Vision, audio?
Size tierFlagship, mini or nano? Smaller is faster and cheaper
ReasoningDoes it think before answering? Can you set the effort?
Context windowHow many tokens fit in one request?
PriceInput, cached input and output are priced separately
AvailabilityWhich regions, which deployment types?
LifecycleWhen does this version retire? You will re-evaluate

The rule that saves money. Start with the smallest model that passes your harness. Move up a tier only when a measured failure requires it, and keep the measurement.

Our choice

gpt-5.4-mini for chat and triage, text-embedding-3-small for retrieval in Week 6.

Identity

No keys: every call carries a short-lived token

The same code runs on your laptop and in Container Apps: DefaultAzureCredential finds az login in one place and the app's managed identity in the other.

Authorization is RBAC

A valid token is not enough: the identity needs a role, and only the one it needs

Role (previous name)Can doWho has it here
Foundry User
Azure AI User		Call models, use agents and project data: the data planeYou, and your app's managed identity
Foundry Project ManagerManage a project, assign Foundry User in itNobody
Foundry OwnerFull access to projects and resourcesNobody
Foundry Account OwnerDeployments, guardrails, connections: the control planeYou, as subscription owner

Least privilege

The running service needs the data plane only. If it is compromised, it cannot create deployments or change safety settings.

Agents get identities too

Foundry agents receive their own Entra agent identity: a tool call is authorized as the agent, not as a shared key.

The Responses API, from scratch

One request, typed output, token usage. Then the four options you will choose deliberately: effort, caching, state and streaming.

Anatomy

One request in, a list of typed items out

Lab Part 2 · your first call

from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import OpenAI

token = get_bearer_token_provider(
    DefaultAzureCredential(), "https://ai.azure.com/.default")
client = OpenAI(base_url=FOUNDRY_OPENAI_ENDPOINT, api_key=token)

r = client.responses.create(
    model="gpt-5.4-mini",          # the deployment name
    instructions="You are Lakeshore Ride support. One sentence.",
    input="Can I end my ride at any station?",
)
print(r.output_text)
print(r.usage.input_tokens, r.usage.output_tokens)
Requestmodel · instructions · input · tools · text.format · reasoning · previous_response_id · stream
Responseid · output: items such as message, reasoning, function_call · output_text · usage

Why Responses, not Chat Completions? It models what agents need: typed items, server-side state, built-in tools, reasoning that persists across turns. New platform features are built on it.

The api_key slot takes a token provider. The SDK asks it for a fresh Entra token on every request. There is no key to leak.

Two inputs, and memory

Instructions are yours and trusted; input is the user's and never trusted

instructions

Who the model is and how it behaves. Written once, in code, stable. Good for caching.

input

What the user said. Changes on every request. Never trusted: Week 10 shows why.

The model has no memory: each call stands alone. Three ways to carry a conversation:

ApproachHowTrade-off
Client-side historyResend previous messages as inputFull control; you manage truncation
previous_response_idPoint at the last response; the service chains historySimple; needs server-side storage
Conversations APIA durable conversation objectShared across clients; what Foundry agents use

Server-side state is convenient, not free: the whole history is processed as input tokens on every turn.

State and streaming

Streaming changes when users see words, not when you finish

0.8 sfirst words on screen
1.9 scomplete answer

One streamed answer on the course sandbox. With stream=True the API sends events: response.created, many response.output_text.delta, then response.completed.

For a chat window this is the difference between "fast" and "broken". For a JSON API such as /v1/classify it buys nothing.

first = client.responses.create(

Without previous_response_id the model does not know Ada. With it, the service chains the history, and you still pay for it as input.

Reasoning

Reasoning effort is a dial: measure where to set it

"A member rides an e-bike for 40 minutes at $0.18 a minute. What do they pay?" One run on the course sandbox:

none (default)0 tokens · $7.20
low25 tokens · $7.20
medium25 tokens · $7.20
high40 tokens · $7.20
xhigh72 tokens · $7.20

Bars show hidden reasoning tokens, billed as output. Every setting gave the same answer.

Easy task: none wins

Same answer, fastest, cheapest. Picking one of six categories is an easy task.

Hard task: measure

Several rules at once, multi-step arithmetic, plans: more effort can change the answer.

Two facts about gpt-5.4-mini. The default effort is none. Sampling settings such as temperature work only with none.

Tokens, cost and latency

Output tokens drive both the bill and the wait

Token cost

(input − cached) × pin + cached × pcached + output × pout

Usage totals already include cached input and hidden reasoning. Do not add them again. Rates here are per token.

Latency

time to first token + visible output tokens / tokens per second

Queueing, prompt processing and reasoning come first; then generation.

LeverCostLatency
Shorter output: a label, a sentence, a JSON objectLargeLarge
Lower reasoning effortFewer reasoning tokensShorter first token
Smaller model tierLower price per tokenUsually faster
Stable prefix first, so it is cachedCached input is discountedFaster prompt processing
Fewer calls per request (Week 7)LinearLinear on the critical path

Prompt caching

A repeated prefix is cached: cheaper and faster, with no code change

The whole handbook in the instructions, three different questions, one run on the course sandbox:

QuestionInput tokensCached
Can I bring my dog on a bike?1,7410
How long is a day pass valid?1,7401,280
Is there a student plan?1,7381,280

Read it from usage.input_tokens_details.cached_tokens.

How it works. When the first 1,024 or more tokens of a request match a recent request, they are served from cache.

So, put stable content first

Instructions, tool definitions, examples, then the user's message last.

Never a timestamp at the top

One changing token early in the prompt breaks the match for everything after it.

Part 3 · Lab Part 3

Structured output: from prose to contracts

A service cannot parse prose. The API can guarantee the shape; your instructions supply the judgment.

Structured output

Shape is guaranteed by the schema. Judgment is not

LevelThe API guaranteesFails how
Ask in the promptNothingProse, invalid JSON, wrong fields
JSON modeValid JSONAny shape, invented values
Structured outputsJSON that matches your schemaA refusal, or a wrong but valid value

Four rules. Literal removes invention. Field descriptions are prompt. The schema cannot know your business rules. Validate at the boundary anyway.

app/contract.py, simplified · Lab Part 3

class TicketLabel(BaseModel):
    category: Literal["billing", "bike_issue", "station_issue",
                      "account", "safety", "other"]
    urgency: Literal["low", "medium", "high"]
    summary: str = Field(description="One sentence, at most 25 words.")

parsed = client.responses.parse(
    model=MODEL, instructions=RULES, input=ticket,
    text_format=TicketLabel,
)
label = parsed.output_parsed   # a TicketLabel, not a string

The schema constrains generation itself: the model cannot produce a token that breaks it.

Part 4 · Lab Part 4

Prompts are code, improved by measurement

They live in git, they have bugs, and they need tests. The harness is the test.

Writing instructions

A triage policy a new support agent could follow

PartExample for triage
Role and task"You triage Lakeshore Ride support tickets."
DefinitionsOne line per category, with typical cases
RulesWhen urgency is high, medium, low, stated so a person could apply them
Tie-breakers"Safety beats everything. A refund request is billing, even if a broken bike caused it."
OutputSummary length; no personal data
ExamplesThree or four short tickets, chosen for the hard cases

Small models read literally

Put the rules that matter most first. Say what to do when two rules conflict. One worked example beats ten adjectives.

Write at the right altitude

Specific enough to decide a case; general enough for tickets you have not seen.

The core skill of the course

Improve by measurement, not by impression

  1. Run the harnesscourse.check(5, in_process=True) scores your local code in a minute.
  2. Read the missesNot the score. For each miss: what rule would a new agent need?
  3. Change one thingOne rule, one example. Otherwise you will not know what helped.
  4. Measure againKeep the change only if the score moves for a reason you can explain.

Know your noise

The same prompt can move a point or two between runs. One point is noise; five is signal.

Do not overfit

We grade on tickets you have not seen. A rule that names a public ticket's words is an answer, not a rule.

Stop and deploy

At the 45-minute mark deploy your best version (Part 5). Then keep going to 100 and redeploy.

Foundry Agent Service

Beyond one request: when an agent runs, for how long, and as whom

Routines: when

A schedule (at most once every five minutes), a set time, a new GitHub issue or a Teams message starts a prompt or hosted agent. Success means "delivered", not "finished".

Long-running: how long

Work outlives the client connection. A dead process is detected and the handler re-entered with the same input; streams resume from a cursor. Preview.

Autopilots: as whom

A hosted agent published as a blueprint. Each instance gets an agent identity and an agent user account: its own mailbox and Teams presence.

Recovery is re-entry, not replay. The handler starts again from the top, so every side effect must be safe to repeat or recorded as done: Week 7's checkpoints, Week 10's idempotency keys.

Summary

What to remember

  • Foundry is one resource with projects. Code calls a deployment by name.
  • The deployment type decides where inference runs and how you pay. Start with Global Standard.
  • Quota is tokens and requests per minute. Over either you get 429: back off, honor Retry-After.
  • No keys. Entra ID tokens, managed identity, least-privilege roles.
  • Output and reasoning tokens drive cost and latency. Effort is a dial; none by default.
  • A stable prefix is cached: instructions first, the user's message last.
  • Structured output fixes the shape; instructions carry the judgment.
  • Change one thing, measure, read the misses. Then deploy.
