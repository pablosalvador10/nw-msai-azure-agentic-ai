Terraform: infrastructure as text

Terraform turns text files into cloud resources. You write the end state you want ("a container registry named X, a model deployment named Y"); Terraform compares it with what exists and makes the minimum changes.

Repeatable

The same files give every student the same platform, and give you the same platform back after destroy.

Reviewable

A change is a diff in a file, and plan shows its effect before anything happens.

Explainable

The files are the documentation of what you run.

*.tf filesdesired state
terraform.tfstatewhat Terraform created
Azurewhat exists
→
terraform planthe diff
→
terraform applyexecutes exactly the plan; updates Azure and the state

1 · A resource block

Everything in Terraform is a block. A resource block has a type (azurerm_container_registry, defined by the Azure provider), a local name (this, used to refer to it from other blocks) and arguments. The notebook prints infra/registry.tf:

print((course.INFRA / "registry.tf").read_text())
  • local.name and local.rg_name are locals: values computed once in main.tf.
  • local.tags adds the same tags to every resource, so you can find and bill them together.
  • Other blocks refer to this one as azurerm_container_registry.this.login_server. That reference is also how Terraform knows the order: the Container App cannot be created before the registry it pulls from.

2 · Inputs, computed values, outputs

KindFileRole
Variablesvariables.tfInputs you set, in terraform.tfvars
Localsmain.tfValues derived from inputs
Outputsoutputs.tfWhat you read back: endpoints, names

terraform console evaluates any expression against your real configuration:

for expression in ["var.student_id", "local.name", "local.foundry_project_endpoint", "var.chat_model"]:
    result = subprocess.run(
        [shutil.which("terraform"), "-chdir=infra", "console"], input=expression, capture_output=True, text=True
    )
    print(f"{expression:32s} = {result.stdout.strip()}")

3 · State: Terraform's memory

terraform.tfstate maps each block to the real Azure resource it created. Without it, Terraform would not know that azurerm_container_registry.this is the registry acr… in your subscription.

course.tf("state", "list")
course.tf("state", "show", "azurerm_cognitive_deployment.chat")

Treat the state file like a password. It can contain secrets, so it is gitignored. Teams keep it in a shared, locked storage account instead: a remote backend.

4 · Change something, safely

The notebook adds a tag to every resource, shows the plan, and does not apply it. Any file ending in .auto.tfvars in infra/ is read automatically.

exercise = course.INFRA / "zz_exercise.auto.tfvars"
exercise.write_text('tags = { owner = "me", purpose = "terraform-primer" }\n')
try:
    course.tf("plan", "-input=false", "-no-color")
finally:
    exercise.unlink()
    print("Removed", exercise.name)
In the planMeaning
~ update in-placeAzure can change the resource without recreating it. Tags are always in place.
-/+ destroy and then create replacementThe change forces a new resource, for example a rename. That deletes data: always read the plan before you apply.
The summary lineCounts adds, changes and destroys. Before every apply, make sure those numbers are what you expect.

What to remember

  1. Files describe the end state; plan shows the diff; apply executes exactly the plan.
  2. References between blocks define the order.You rarely need depends_on.
  3. State is Terraform's memory.Keep it private; share it through a remote backend in teams.
  4. Never edit Terraform-managed resources in the portal.The next plan will try to undo your change.

FastAPI: an HTTP API in Python

Your service is an HTTP API: programs send it a request and get a response. FastAPI is a Python framework for writing one. You declare routes as functions and the shapes of requests and responses as Pydantic models; FastAPI does the parsing, validation, error messages and documentation.

Part of an HTTP exchangeExample
MethodPOST (send data), GET (read)
Path/v1/classify
HeadersContent-Type: application/json, X-Request-ID: 42
Body{"id": "t1", "text": "My brake is broken"}
Status code200 OK, 401 not authenticated, 413 too large, 422 invalid input, 429 slow down, 500 server bug, 503 not ready
The status code is part of your contract. The harness checks it as carefully as the body.

1 · A complete API in ten lines

TestClient calls the app directly, in this process: no server, no port, no network. It is how our tests and the harness's in-process mode work.

from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

demo = FastAPI()


class FareRequest(BaseModel):
    minutes: int = Field(ge=0, le=1440, description="Ride length in minutes")
    ebike: bool = False


class FareResponse(BaseModel):
    total: float


@demo.post("/fare")
def fare(body: FareRequest) -> FareResponse:
    rate = 0.40 if body.ebike else 0.20
    return FareResponse(total=round(1.25 + rate * body.minutes, 2))


client = TestClient(demo)
response = client.post("/fare", json={"minutes": 30, "ebike": True})
print(response.status_code, response.json())

2 · Validation is free

Send bad input. You did not write a single if: the Pydantic model is the validation, and FastAPI answers 422 with a precise message.

for bad in [{"minutes": -5}, {"minutes": "half an hour"}, {}]:
    r = client.post("/fare", json=bad)
    print(r.status_code, r.json()["detail"][0]["msg"])

3 · def or async def

def

Routes run in a thread pool. Fine for quick work.

async def

Routes run on the event loop. While one request waits (for a model, a database, another API), the loop serves others.

Our routes are async def because nearly all their time is spent waiting for a model. The one rule: inside async def, never call something slow that is not awaited, or every request waits behind it.

4 · The course service, in-process

The same technique works on the real service. Offline mode replaces the models with deterministic stand-ins, so this needs no Azure.

from app.config import LLMMode, Settings
from app.main import create_app

offline = Settings(llm_mode=LLMMode.OFFLINE, student_id="demo", _env_file=None)
with TestClient(create_app(offline)) as service:
    print(service.get("/v1/info").json())
    print(service.post("/v1/classify", json={"id": "t1", "text": "I was charged twice"}).json())
    routes = service.get("/openapi.json").json()["paths"]
    print("Routes:", ", ".join(routes))

5 · A real server

To run the service as a server, open a terminal in fy26/:

uv run uvicorn app.main:app --reload

Then open http://localhost:8000/docs: an interactive page generated from your models, where you can call every route. --reload restarts the server when you save a file. Stop it with Ctrl+C.

6 · Exercise

A route that can say "not found"

Add a GET /stations/{station_id} route to demo that returns app.domain.get_station(station_id), and answers 404 when the station does not exist (the function returns a dict with an error key). Hint: from fastapi import HTTPException and raise HTTPException(status_code=404, detail=...). The notebook's check cell expects LS-05 to be Central Station and LS-99 to return 404.

What to remember

  1. A route is a function; its parameters and return type are the contract.
  2. Pydantic models validate input for youand document the API at /docs.
  3. Status codes are part of the contract:4xx means the caller's fault, 5xx means yours.
  4. TestClient tests the whole app without a server.

Containers and Azure Container Apps

A container image is your program plus everything it needs to run (Python, packages, files), frozen into one artifact. A container is a running copy of an image. A registry stores images. The same image runs on your laptop, a teammate's and in Azure, which removes "it works on my machine". Azure Container Apps runs your image for you: it gives it an HTTPS address, restarts it if it crashes, adds copies under load and removes them when idle.

1 · The Dockerfile

Two stages. The first installs dependencies with uv from the lockfile; the second copies only the result and the code, and runs as a non-root user. Smaller image, fewer things to attack, faster starts. The notebook prints the Dockerfile and .dockerignore, which decides what is sent to the build.

2 · Images in your registry

az acr build sends the build context to Azure and builds there, so you never need Docker on your laptop. Each deploy pushes a new tag; old tags stay, which is how you roll back.

course.run(["az", "acr", "repository", "show-tags", "--name", ACR, "--repository", "app",
            "--orderby", "time_desc", "-o", "table"])

3 · Revisions and replicas

The active revision serves the traffic. With min_replicas = 0, the replica list is empty while nobody calls the service.

course.run(["az", "containerapp", "revision", "list", "-n", APP, "-g", RG, "--query",
            "[].{revision:name, active:properties.active, created:properties.createdTime, "
            "health:properties.healthState, replicas:properties.replicas}", "-o", "table"])

4 · Cold start, measured

Call /health twice. If the app had scaled to zero, the first call waits for a replica to start (pull the image, start Python, build the handbook index). The second call is fast.

for attempt in (1, 2):
    start = time.perf_counter()
    status = httpx2.get(f"{course.app_url()}/health", timeout=120).status_code
    print(f"call {attempt}: {status} in {time.perf_counter() - start:.1f} s")

5 · Logs

What your service prints goes to the console log. Each request line carries its request_id, which also comes back in the X-Request-ID response header: the thread that ties a user's complaint to a log line.

course.run(["az", "containerapp", "logs", "show", "-n", APP, "-g", RG, "--tail", "20", "--format", "text"])

What to remember

  1. Image = program + dependencies, built once, run anywhere.Tag every build; never reuse a tag.
  2. A deploy creates a new revision;the old one keeps serving until the new one is ready.
  3. Scale to zero saves moneyand costs a slow first request.
  4. Probes tell the platformwhen to restart (liveness) and when to send traffic (readiness).

Identity and access: no keys

API keys are the most common way cloud credentials leak: pasted in a notebook, committed to Git, shared in a chat. This course uses no keys. With keys turned off on Foundry (local_auth_enabled = false), a request needs a valid token and a role assignment. Nothing to leak, nothing to rotate.

1 · Look inside a token

A token is a signed JSON document. The middle part is readable: it says who you are (oid), who the token is for (aud) and when it expires (exp). The notebook prints the claims, never the token.

token = DefaultAzureCredential().get_token("https://ai.azure.com/.default")
payload = token.token.split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
for key in ["aud", "iss", "oid", "upn", "name", "exp"]:
    value = claims.get(key)
    if key == "exp":
        value = f"{value}  ({datetime.fromtimestamp(value):%H:%M})"
    print(f"{key:5s} {value}")

2 · Where DefaultAzureCredential gets it

  1. Environment variablesService principals in CI.
  2. Workload identityKubernetes.
  3. Managed identityIn Azure. Our Container App sets AZURE_CLIENT_ID so it picks the user-assigned identity id-….
  4. Azure CLIOn your laptop: your az login.

It tries the sources in order and uses the first that works. Same code, two places, no secrets.

3 · Who can do what on your Foundry resource

course.run(["az", "role", "assignment", "list", "--scope", foundry_id, "--query",
            "[].{who:principalName, type:principalType, role:roleDefinitionName}", "-o", "table"])

You should see two assignments of Foundry User (shown as "Azure AI User" while Microsoft renames it): one for you, one for the app's managed identity. That is least privilege: enough to call models and run agents, not enough to delete the resource or change who has access.

4 · Without a token, nothing works

r = httpx2.post(f"{out['foundry_openai_endpoint']}responses", json={"model": out["chat_deployment"], "input": "hi"})
print(r.status_code, r.text[:200])

A request with no Authorization header is refused: there is no key to fall back on.

What to remember

  1. Identities, tokens and roles replace keys.Tokens expire within the hour; roles are revoked in one place.
  2. DefaultAzureCredential makes the same code workon your laptop (your login) and in Azure (managed identity).
  3. Grant the smallest role that works,on the smallest scope that works.

The harness: measure, don't guess

A model gives a different answer every time you ask, so "it worked when I tried it" proves little. A harness asks the same questions every time, records every request and response, and turns them into a score. It is to an AI system what a test suite is to ordinary code, and the only honest way to say "this change made things better".

Dataharness/data/week*.jsonl
→
Clientcalls your service; retries 429/503; records every exchange
→
Checksscore 0 to 1, plus a detail line
→
Engine and reportscore out of 100; report and proof with a SHA-256 digest
PartFileRole
Clientharness/client.pySends HTTP requests, retries on 429/503, records every exchange as evidence
Checksharness/checks/week*.pyFunctions that return a score from 0 to 1 and a detail line
Dataharness/data/week*.jsonlThe public questions and expected answers
Engine and reportharness/engine.py, harness/report.pyWeighted score out of 100; a Markdown report and a JSON proof

The grade uses unseen data. The instructors run the same engine with more questions you have not seen. Improve the capability, not the answers to the public questions.

1 · A check is a small function

import inspect

from harness.checks import week05

print(inspect.getsource(week05._accuracy))

2 · Run it without Azure

in_process=True runs the service inside the notebook. LLM_MODE=offline swaps the models for deterministic stand-ins, so the run costs nothing and takes seconds. The offline score is meaningless as a grade; the point is the mechanics.

os.environ["LLM_MODE"] = "offline"
try:
    proof = course.check(5, in_process=True)
finally:
    os.environ["LLM_MODE"] = "foundry"

3 · Read the proof

Each check keeps the exchanges it made. When a check fails, this is where you find out why: the exact request, the exact response, the status and the latency.

print("score: ", proof["score"])
print("digest:", proof["digest"])
check = next(c for c in proof["checks"] if c["id"] == "w05.validation")
for exchange in check["exchanges"]:
    print(exchange["status"], exchange["method"], exchange["path"], json.dumps(exchange["request"])[:60])

4 · Write your own check

A check takes a Context (with ctx.target to call the service) and returns (score, detail). This one verifies that the service reports a real version, not dev.

def version_is_set(ctx: Context) -> tuple[float, str]:
    info = ctx.target.get("/v1/info").json()
    ok = info.get("version") not in (None, "", "dev")
    return (1.0 if ok else 0.0), f"version = {info.get('version')!r}"


settings = Settings(llm_mode=LLMMode.OFFLINE, student_id="demo", app_version="dev", _env_file=None)
with TestClient(create_app(settings)) as client:
    print(version_is_set(Context(target=Target(client=client), week=5)))

What to remember

  1. Measure before and after every change.One score, same data, same checks.
  2. Read failures in the proof, not in your head:request, response, status, latency.
  3. Public data is for learning; the grade uses unseen data.Generalize.
  4. A check is a function.When you find a failure mode, write a check for it.
